# Verification — domain 13 (lattice reduction under stress)

Every command below was run on 2026-09-21 from `domains/13-lattice-reduction-stress` in this
repository, against the files as published. The six swept runs in `results/` were **not**
regenerated: they are the evidence this domain's notes cite, they carry the pre-2026-09-20 Hermite
convention that §4 of `README.md` exists to warn about, and re-running them at one thread costs
hours. What was re-run is the test suite, the milestone-0 API probe, the load-bearing planted-vector
check, and the estimator path on a published parameter set.

**Environment.** The sage environment interpreter — CPython **3.12.14** — which is the one
interpreter in which **fpylll 0.6.4**, **G6K 0.1.2**, **SageMath 10.9** and the lattice estimator
(revision `53da5982597709ba0fdf94ea37a84d822310fd84`) all import, with **numpy 2.4.6**, **sympy
1.13.1**, **pytest 9.0.2** and **hypothesis 6.151.9**. There is no subprocess boundary: the
pipeline, the engines and the estimator run in one process. None of the three tools is
pip-installable in the ordinary sense — the fpylll wheel vendors its own libfplll/libgmp/libmpfr and
declares no dependencies, G6K has never had a published wheel and is built from source against a
linkable fplll, and the estimator is not on PyPI at all — so they are provided by that environment
and by two checkouts in a sibling tools directory outside this repository, registered by
`scripts/move_tools.py`. Host: Ubuntu 24.04.4, x86_64, kernel 7.0.0-31, 12 cores. `engine.threads`
is **1**; see the note on the thread row below.

## What was not run, and why

- **The dimension sweep.** `cli sweep` rebuilds the six run directories in place. They are the
  evidence `notes/09` and `README.md` §2 cite, they carry the pre-fix Hermite convention that §4
  warns about, and at one thread dimension 130 alone is about ten minutes. Each directory ships its
  own `config.yaml`, which is what a re-runner needs.
- **Dimension 160 was never solved, by this build or any earlier one.** The time guard refused every
  block size above 50 — projecting 728 s, 3,985 s and 21,828 s at β = 60, 70 and 80 from the
  measured 132.8 s at β = 50 — and the row is recorded as a refusal with its projections rather than
  as a large number.
- **Anything at the production parameters.** §6 of `README.md`. The estimator was run; no lattice
  was built and no reduction was attempted at ν = 256, and the guard that makes that an act rather
  than a drift is still in place and still tested.
- **The memory model.** `scripts/profile_hardware.py` was not re-run here. Its earlier claim that
  the model over-predicts by ≈ 15× is **withdrawn in the source notes**, because the footprint it
  compared contains no sieve database — `Siever.db_size()` reports 500 at every block size and every
  tour count, and peak RSS is flat across five consecutive β = 80 tours (123 → 124 MiB) where the
  model predicts 258 MiB. What stands is the confirmed ≤ 141 MiB bound at β = 90, measured at
  **112 MiB** after subtracting the fixed 65 MiB import cost each forked child pays. The per-entry
  constant is unmeasured in either direction and `sieve_block_size_max: 80` rests on it.
- **Any multi-threaded run.** Four threads is not a measurement here; see the reproducibility row.
- **Nothing was written to or read from the read-only research tree.** The only operation this
  domain has ever performed against that path is moving its own tool checkouts *out* of it, verified
  before anything was removed; no source file names it, and a test asserts that.
