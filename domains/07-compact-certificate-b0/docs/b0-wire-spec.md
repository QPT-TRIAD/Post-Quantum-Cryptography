# CE-QS profile B0 — normative wire specification (v1.44 frame format)

This document is the complete input for an independent implementation. It was
written from the v1.44 constants and rules, not from the reference source, so
that a second implementation built from it alone can be cross-validated
against the reference on generated vectors. Where this text is ambiguous, the
ambiguity is a finding against this document.

**Paths.** Paths that name other project files are relative to the repository root,
and version suffixes have been dropped from file names. The independent B0
implementation, the generated vectors and the check results belong to the
independent-audit-stack domain (`domains/11-independent-audit-stack/independent-b0/`);
this specification refers to them and does not duplicate them. A file named here that
is not copied into this repository is marked as such.

## 1. Parameters

| symbol | value | meaning |
|---|---|---|
| N | 64 | seats, indices 0..63 |
| QUORUM | 43 | signatures per certificate (exactly) |
| MIN_OVERLAP | 22 | = 2·QUORUM − N; minimum common seats of two valid frames |
| MAGIC | ASCII `CQ44` (4 bytes) | frame magic |
| VERSION | 44 | u16 |
| SUITE_B0 | 0x44B0 | u16 |
| COUNT | 43 | u16, always QUORUM |
| HEADER_BYTES | 208 | fixed header length |
| MAX_FRAME_BYTES | 32768 | inclusive upper bound on a frame |

## 2. Hash

`H(label, part_1, …, part_k)` = SHAKE256 over the concatenation, for each of
label, part_1, …, part_k in order, of `len(part) as u64 big-endian ‖ part`,
squeezed to **64 bytes**. All parts are byte strings; anything else is an error.

## 3. Registry and configuration

A registry is an ordered list of exactly 64 distinct non-empty public keys
`pk_0 … pk_63` and a byte string `scheme_id`.

`cfg = H(b"CQ44/cfg/B0", scheme_id, pk_0, pk_1, …, pk_63)` (64 bytes).

## 4. Vote message

For seat `i` (0 ≤ i ≤ 63), 64-byte `domain` and 64-byte `message`:

`vote_i = b"CQ44/B0/VOTE" ‖ cfg ‖ domain ‖ message ‖ (i as one byte)`.

## 5. Signature provider (toy, for vectors)

The B0 profile is generic over a signature scheme with fixed signature width
`W` bytes. For cross-validation vectors the deterministic **toy** scheme is:

- `sk_i = b"SK" ‖ i as u16 big-endian`, `pk_i = b"PK" ‖ i as u16 big-endian`
- `sign(sk, msg) = SHAKE256(b"TOYSIG" ‖ sk ‖ msg)` squeezed to `W = 32` bytes
- `verify(pk, msg, sig)`: recompute with `sk = b"SK" ‖ pk[2:]` and compare (constant width 32).
- `scheme_id = b"toy-shake-32"`.

## 6. Frame layout (big-endian)

```
header (208 B) = MAGIC(4) ‖ VERSION u16 ‖ SUITE u16 ‖ cfg(64) ‖ domain(64) ‖ message(64)
               ‖ COUNT u16 ‖ WIDTH u16 ‖ PAYLOAD_LEN u32
payload        = bitmap u64 (bit i set ⇔ seat i signed) ‖ sig_1 ‖ sig_2 ‖ … ‖ sig_43
```

- The 43 signatures appear in **ascending seat order** of the set bits.
- `WIDTH` = signature width W; `PAYLOAD_LEN` = 8 + 43·W.
- Encoding requires exactly 43 distinct seats in 0..63, a 64-byte domain and
  message, and every signature exactly W bytes.

## 7. Verification (`verify_b0(frame, registry, expected_cfg)`) — all checks, any failure rejects

1. frame is a byte string; 208 ≤ len(frame) ≤ 32768.
2. header fields: MAGIC, VERSION = 44, SUITE = 0x44B0, COUNT = 43.
3. `PAYLOAD_LEN` = number of bytes after the header (no truncation, no trailing bytes).
4. header cfg equals `expected_cfg` **and** equals the recomputed `cfg` of the registry.
5. WIDTH equals the provider width and is positive; payload length = 8 + 43·WIDTH.
6. bitmap popcount is exactly 43.
7. for each set bit i in ascending order with position p (0-based among set bits): the
   signature at payload offset `8 + p·WIDTH` verifies under `pk_i` over `vote_i`.

Result: `(cfg, domain, message, width, bitmap, seats)`.

## 8. Extraction (`extract_b0(frame0, frame1, registry, expected_cfg)`)

1. verify both frames (any failure rejects the pair).
2. reject if cfg differ, if domain differ, or if **message equal** (equal messages are not a conflict).
3. `common = bitmap0 AND bitmap1`; reject if popcount(common) < 22 (impossible for two valid frames).
4. output, ascending by seat: `(seat, position0, position1)` for every set bit of `common`,
   where position is the seat's 0-based position among the frame's set bits.

## 9. Blame (`verify_blame_b0(frame0, frame1, registry, expected_cfg, seat)`) → bool

True iff `0 ≤ seat ≤ 63`, both frames verify, domains equal, messages differ,
and `seat` is set in both bitmaps. Any exception path → False.

## 10. Vectors

`b0_vectors.json` (generated by the reference with the §5 toy scheme; the file lives at
`domains/11-independent-audit-stack/independent-b0/b0_vectors.json`, together with
`gen_b0_vectors.py`, `check_vectors.py`, `SPEC_GAPS.md` and the recorded check results)
has top-level
`registry` = {`public_keys`: 64 hex strings, `scheme_id`: plain ASCII text}, `cfg` (hex), and
`cases`, each with `kind` ∈ {`conflict`, `same-message`, `other-domain`, `mutated`,
`truncated`, `trailing`}. A `conflict` case carries `domain`, `message0`, `message1` (hex),
`seats0`, `seats1`, `frame0`, `frame1` (hex), `extract` (list of `[seat, pos0, pos1]`) and
`blame` (map seat → bool). `same-message`/`other-domain` cases carry `frame0`, `frame1` and
`expected_extract = "reject"`; `mutated`/`truncated`/`trailing` cases carry `frame` and
`expected_verify = false`. An independent implementation must reproduce every frame
byte-for-byte and every verdict.

## 11. Clarifications made normative after the independent implementation (2026-09-13)

An implementer working from §§1–10 alone
(`domains/11-independent-audit-stack/independent-b0/b0_indep.py`) agreed
with the reference on 6,701/6,701 checks over 900 vectors, and reported 18 points where the
text left a choice. The choices below are now normative; items 1–4 were observable on the
wire or in verdicts and are the important ones.

1. **Bitmap bit numbering.** "bit i" is the value bit 2^i of the u64 (seat 0 = least
   significant bit); the u64 is serialised big-endian. (Gap 1.)
2. **`encode` signature.** `encode(registry, domain, message, secret_keys, seats)` where
   `secret_keys` is a list of 64 secret keys aligned index-for-index with
   `registry.public_keys`; seat i is signed with `secret_keys[i]`. The §5 toy derivation
   `sk = b"SK" ‖ pk[2:]` is a property of the toy scheme only. (Gap 2.)
3. **Toy verify** additionally requires `pk[:2] == b"PK"` and `len(pk) == 4`; otherwise
   reject. (Gap 3.)
4. **Vector file layout** is as stated in §10 above; `scheme_id` is ASCII text, public keys
   are hex. (Gap 4.)
5. **Rejection form.** Verification and extraction reject by raising a typed error; `blame`
   maps every error to `False`. Any implementation-language exception inside these
   procedures counts as a rejection, never as acceptance. (Gaps 5, 9.)
6. **Input types.** `frame`, `domain`, `message`, `expected_cfg`, keys and `scheme_id` are
   immutable byte strings only (`bytes`; not `bytearray`, `memoryview` or text);
   `expected_cfg` is exactly 64 bytes; `seat` is an integer that is not a boolean and is in
   0..63. Anything else rejects. (Gaps 6, 7, 8.)
7. **Registry validation** (64 distinct non-empty keys, `scheme_id` bytes) is performed by
   `cfg()` and therefore by every verification through §7.4. (Gap 10.)
8. **Redundant clauses** §7.5, §8.2, §8.3 and the omissions in §9 are retained as defence in
   depth; they cannot change any verdict on inputs that pass the earlier checks. Check order
   is unspecified; only diagnostics may differ. (Gaps 11–14.)
9. **Concatenation vs `H`.** §4 (`vote_i`) and §5 (toy signing) use plain concatenation;
   only §2/§3 use the length-prefixed `H`. Do not route the vote or the toy input through
   `H`. (Gap 15.)
10. **Encode-side bound.** `encode` must refuse to emit a frame longer than 32,768 bytes
    (W ≤ 757 for the 208 + 8 + 43·W layout). (Gaps 16, 17.)
11. **"constant width 32"** means a fixed-length signature of 32 bytes compared with a
    constant-time comparison. (Gap 18.)
